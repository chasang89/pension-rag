# ADR 0002: 로컬 개발 환경(Docker)과 색인 파이프라인 확정

- 날짜: 2026-09-08
- 상태: 확정
- 관련 커밋: `2f744a8`(Docker), `ebcbb1f`(ingestion)

## 배경

[ADR 0001](0001-project-kickoff.md)에서 스택을 확정하고 법령 코퍼스 수집까지 마쳤으나,
`docker compose up`이 동작하지 않아 아무것도 실행할 수 없는 상태였다.
compose가 `Dockerfile.rag-core`, `Dockerfile.gateway`를 참조하는데 두 파일 모두 없었고,
nori 플러그인은 `# TODO` 주석으로만 남아 있었다.

## 결정

### 1. Elasticsearch는 nori를 구운 커스텀 이미지로

공식 이미지에는 nori가 없다. 한국어 법령의 BM25 검색은 형태소 분석이 사실상 전제이므로
`analysis-nori`를 설치한 이미지를 빌드한다.

검증: `"연금계좌 세액공제 한도"` → `연금 / 계좌 / 세액 / 공제 / 한도`로 분해됨을 확인.

### 2. 청킹은 조(條) 단위, 초과 시 항(項) 단위

법령 인용 단위가 조이므로 조를 기본 단위로 한다. 1,200자를 넘으면 항으로 쪼개고,
항도 넘치면 100자 겹침을 두고 자른다. "삭제" 조문은 제외한다.

수집 스크립트가 이미 조·항·호까지 파싱해두어 원문 파싱은 하지 않는다.
이 덕분에 당초 5~8시간으로 잡았던 작업이 크게 줄었다.

| 법령 | 청크 |
|---|---:|
| 국민연금법 | 196 |
| 국민연금법 시행령 | 195 |
| 근로자퇴직급여 보장법 | 77 |
| 근로자퇴직급여 보장법 시행령 | 91 |
| 소득세법 | 521 |
| 소득세법 시행령 | 1,061 |
| 조세특례제한법 | 1,328 |
| 조세특례제한법 시행령 | 2,244 |
| **합계** | **5,713** |

조세특례제한법 시행령 하나가 전체의 39%다. 조문당 평균 3,182자로 가장 길다.
연금 절세의 핵심 근거(IRP·ISA·연금저축)가 대부분 여기 있어 물량이 많은 것은 자연스럽다.

### 3. BM25와 벡터를 한 인덱스에

`nori` 분석기 `text` 필드와 `dense_vector` 필드를 같은 인덱스에 둔다.
하이브리드 검색(RRF)에서 두 랭킹을 같은 문서 집합에 대해 매길 수 있어야 하기 때문이다.

### 4. 임베딩 차원은 1024 (스펙 문서 정정)

[스펙 v2](../research/연금절세_RAG_스펙_v2.md)에 `dims=1536`으로 적혀 있으나 이는
OpenAI `text-embedding-3-small` 기준이다. **채택 모델인 bge-m3는 1024차원이다.**
그대로 뒀으면 색인이 통째로 실패했을 값이다.

`settings.embedding_dims`로 한 곳에서 관리하고, 모델 출력·인덱스 매핑과 어긋나면
색인 전에 멈추도록 `embedder`와 `indexer` 양쪽에 검사를 넣었다.

## 작업 중 발견한 문제

### 조문 가지번호 누락 (수정함)

원본 JSON의 `article_no`에는 가지번호가 없다. 제1조와 제1조의2가 모두 `"1"`이다.
그대로 쓰면 출처 표기가 어긋난다 — 소득세법만 168개 조문, 청크의 32%가 해당됐다.
본문 첫 줄의 정식 표기(`제1조의2`)를 정규식으로 뽑아 쓰도록 고쳤다.

법령 RAG에서 출처 정확성은 기능 자체이므로, 인용 표기를 신뢰할 수 있는지
앞으로도 우선 확인할 것.

### 재색인 시 옛 청크 잔류 (미해결)

`chunk_id`를 문서 `_id`로 써서 재실행 시 중복은 쌓이지 않는다. 그러나 **덮어쓰기만 하므로**
법 개정으로 삭제된 조문이나 청킹 규칙 변경으로 사라진 옛 청크는 인덱스에 남는다.
현재로선 `--recreate`가 유일한 정리 수단이다.

코퍼스가 자주 바뀌지 않아 당장 문제는 아니나, 법령 자동 갱신을 붙일 때 반드시 해결해야 한다.
(대안: 색인 실행 ID를 필드로 넣고 이전 실행분을 delete_by_query)

### 코퍼스가 버전 관리되지 않음 (미해결)

`rag-core/data/`가 `.gitignore` 대상이라 코퍼스 JSON 9.4MB가 git에 없다.
법제처 API가 바뀌거나 중단되면 재수집이 불가능해질 수 있다.
릴리스 아티팩트나 별도 저장소로 스냅샷을 남기는 방안을 검토할 것.

## 현재 상태

동작 확인된 것:

- `docker compose -f infra/docker/docker-compose.yml up -d` → 컨테이너 3개 기동
- ES(healthy) / rag-core `:8000/health` / gateway `:8080/health` 모두 응답
- rag-core → ES 컨테이너 네트워크 연결
- 색인 후 BM25·벡터 검색 모두 정상

소득세법 521청크 기준 검색 품질:

| 질의 | 벡터 검색 1위 |
|---|---|
| 연금계좌 세액공제 한도 | 제59조의3(연금계좌세액공제) |
| 퇴직소득세 계산 방법 | 제55조(세율) — 2위 제48조(퇴직소득공제) |
| 이자소득 원천징수 세율 | 제129조(원천징수세율) |

임베딩 속도는 CPU에서 초당 약 2.4청크. 전체 5,713청크에 약 40분.

## 아직 없는 것

| 영역 | 상태 |
|---|---|
| 검색 (retrieval) | `app/retrieval/` 비어 있음. RRF 하이브리드 미구현 |
| 답변 생성 (LLM) | 없음. Claude API 연동 안 됨 |
| API 노출 | `app/main.py`에 `/health`만. 라우터 TODO |
| 게이트웨이 프록시·JWT | `build.gradle.kts` TODO |
| 프론트엔드 | 없음 |

색인은 RAG의 준비 단계다. Retrieval과 Generation이 모두 남아 있어
현재 사용자가 쓸 수 있는 기능은 없다.

## 다음 단계

1. **retrieval** — BM25 + kNN을 RRF로 병합. 설정에 `rrf_k=60`, `bm25_top_k=50`, `vector_top_k=30` 준비됨
2. **답변 생성** — 검색된 조문을 근거로 Claude API 호출, 조문 인용 포함
3. **API 라우터** — `main.py`에 ingestion/retrieval 라우터 등록
4. 게이트웨이 프록시 + JWT
5. 프론트엔드

1~3까지가 "처음으로 제품이 되는" 지점이다.

## 재현 방법

```bash
docker compose -f infra/docker/docker-compose.yml up -d
cd rag-core
python -m app.ingestion.pipeline --all          # 전체 색인
python -m app.ingestion.pipeline --laws 소득세법 --recreate   # 하나만, 인덱스 재생성
```
